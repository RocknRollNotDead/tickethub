Пет-проект для изучения многопоточности

Представляет собой сервис для бронирования билетов на различные мероприятия.
Стэк
Java 17, Spring Boot 4.1.0, MVC с REST-эндпоинтами.

Первая проблема (этап 2) - параллельные запросы на бронирование дают успех, но по факту бронируется только то количество, которое доступно. Это race condition.
Эндпоинт /events/{id}/booking
1 решение - synchronized. Блокируется весь метод, нельзя обернуть его в транзакцию
2 решение - пессимистичная блокировка на уровне бд. блокируется только строка 
3 решение - оптимистичная блокировка. блокируется только просмотр колонки с версией.
в проде выбрал бы пессимистичную, потому что при оптимистичной блокировке появляется дополнительная колонка с версией, и её нужно в каждом кастомном Query указывать.

Этап 3 проблема - иногда походы во внешний сервис бывают долгими, и не хочется долго ждать. Поэтому иногда надо отправлять ответ сразу, а делать асинхронно. Для этого можно создать новые потоки и запускать асинхронно через CompletableFuture.runAsync(). А также запускать несколько через CompletableFuture.allOf() .thenRun(), чтобы делать какие-то действия после завершения.

Этап 4 проблема - при переводе средств от одного к другому одновременно с обратным переводом может возникнуть взаимная блокировка.
Решить это можно с помощью упорядочивания блокировок. Если поступает действие с обьектом 1 и обьектом 2, то всегда сначала захватываем обьект с id 1, а потом с id 2. Что на уровне бд
(SELECT * FROM users WHERE id = user,
что на уровне jvm это можно решить. Я решил с помощью jvm. Ещё можно с помощью оптимистичной блокировки (строка не блокируется, чисто проверяется версия и если что-то не так тупо вылетает ошибка, которую мы ловим и ретраим), но при таком подходе может возникнуть liveLock. Просто ретраится, ретрай занимает место в программе.
Для 2 параллельных запросов ничего страшного, но когда их 100, приложение есть слишком много памяти и слишком долго выполняет, или вообще половину операций может отклонить, поэтому лучше использовать пессимистичную блокировку.
LiveLock это такая же логика как deadlock при synchronized, но вместо блокировки поток сбрасывает ресурс. Каждый раз поток1 захватывает ресурс1 -> поток2 захватывает ресурс2 -> поток1 пытается взять ресурс2, видит что он занят -> поток2 пытается взять ресурс1, видит что он занят -> поток1 освобождает все свои ресурсы -> поток2 освобождает все свои ресурсы -> retry.

Этап 5 проблема - для счётчиков обычный Long не подходит. При параллельных операциях можно поймать race condition. Поэтому для счётчиков используют AtomicLong или вообще класс Counter.
А вот для флагов подходит обычный volatile, потому что его чтение и изменение происходит всегда в разных потоках и операциях. Гонки тут быть не может, только неправильное чтение состояния. (отправили запрос на изменение флага, через 1 мс отправили запрос, где флаг читается, и без volatile флаг не прочитается, а с volatile прочитается сразу после изменения)
CAS(что под капотом у AtomicLong) сравнивает ожидаемое состояние и текущее
