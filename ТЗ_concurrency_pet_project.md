# ТЗ: «БилетHub» — система бронирования билетов с кошельком

## Идея

Сервис на Spring Boot, где пользователи бронируют билеты на мероприятия с ограниченным числом мест и оплачивают их через внутренний кошелёк (баланс). Идея выбрана специально: бронирование мест — классический источник race condition, а переводы между кошельками — классический источник deadlock. Это позволяет естественно упереться почти во все темы из списка, а не притягивать их искусственно.

## Стек

Java 17+, Spring Boot, Spring Data JPA, PostgreSQL (или H2 для простоты), Postman/curl для тестов, JMeter или простой скрипт для нагрузочного теста конкурентного доступа.

## Этап 1. Базовая доменная модель (без потоков)

Сущности: `Event` (название, дата, `totalSeats`, `availableSeats`), `User` (баланс), `Booking` (кто, на что, статус).

REST-эндпоинты: создать событие, посмотреть события, создать пользователя, пополнить баланс.

Цель — рабочий CRUD, чтобы дальше ломать его многопоточностью осознанно.

## Этап 2. Race condition и способы её починить

**Задание:** сделать эндпоинт `POST /events/{id}/book`, который уменьшает `availableSeats` на 1 и создаёт `Booking`.

1. Сначала реализуй его **наивно** (прочитать значение, проверить `> 0`, уменьшить, сохранить). Напиши нагрузочный тест — запусти 50–100 параллельных запросов на событие с 10 местами (через `ExecutorService` в тестовом классе или JMeter). Убедись, что `availableSeats` уходит в минус или продаётся больше мест, чем есть — это и есть race condition, воспроизведённая руками, а не в теории.
2. Почини это **тремя разными способами** (для каждого — отдельная ветка/эндпоинт, чтобы сравнить):
   - `synchronized` метод/блок на уровне сервиса — обсуди, почему это плохо масштабируется (глобальная блокировка на все события сразу, если делать неаккуратно).
   - Пессимистичная блокировка на уровне БД (`@Lock(LockModeType.PESSIMISTIC_WRITE)` в Spring Data JPA).
   - Оптимистичная блокировка (`@Version` на `Event`) с retry-логикой при `OptimisticLockException`.
3. Напиши в README короткое сравнение: что такое race condition, чем synchronized-подход отличается от блокировок на уровне БД, какой подход выбрал бы в проде и почему.

*Закрывает: race condition, синхронизация, монитор, потокобезопасность, happens-before (для объяснения, почему synchronized вообще работает).*

## Этап 3. Асинхронная обработка бронирования через пул потоков

**Задание:** после успешного бронирования нужно: (а) отправить «уведомление» (просто `Thread.sleep(1000)` + лог, эмуляция похода во внешний сервис), (б) записать событие в «аналитику» (тоже имитация задержки).

1. Сделай это через `ExecutorService` — создай bean с `Executors.newFixedThreadPool(n)`, оберни задачи в `Runnable`/`Callable`, вынеси конфигурацию пула в `@Configuration`.
2. Замени часть логики на `CompletableFuture`: запусти уведомление и аналитику **параллельно**, а не последовательно, и объедини их через `thenCombine`/`allOf`, чтобы ответ пользователю ушёл, как только оба завершились (или сразу, если хочешь fire-and-forget — реализуй оба варианта и опиши разницу).
3. Добавь отдельный эндпоинт, который бронирует и сразу отдаёт `202 Accepted`, а обработка идёт в фоне — обсуди в README разницу между асинхронностью и многопоточностью на этом примере.
4. Попробуй `Executors.newCachedThreadPool()` вместо `newFixedThreadPool()` для этой задачи и опиши, чем они отличаются и почему `cached` опасен под нагрузкой (может создать неограниченное число потоков).

*Закрывает: ExecutorService, FutureTask/Callable, CompletableFuture, пулы потоков, асинхронность vs многопоточность, Runnable vs Callable, способы запуска потоков.*

## Этап 4. Кошелёк и Deadlock

**Задание:** добавь перевод денег между пользователями `POST /transfer` (списать у одного, зачислить другому, в одной транзакции/методе).

1. Реализуй наивно через блокировку двух объектов `User` (например, `synchronized(from) { synchronized(to) {...} }`).
2. Напиши тест, который **гарантированно воспроизводит deadlock**: два потока одновременно переводят деньги друг другу навстречу (A→B и B→A) — они захватят объекты в разном порядке и повиснут. Убедись, что видишь зависший поток (можно через `jstack` или просто таймаут в тесте).
3. Почини классическим способом — упорядочивание блокировок (например, всегда сначала блокировать пользователя с меньшим id).
4. В README отдельно опиши разницу между deadlock и livelock, и придумай (не обязательно реализовывать в коде, можно словами + маленьким примером) ситуацию с livelock — например, два потока вежливо уступают друг другу ресурс и оба откатываются бесконечно.

*Закрывает: deadlock, livelock, монитор, синхронизация.*

## Этап 5. Atomic, volatile и статистика в реальном времени

**Задание:** добавь простой счётчик статистики — сколько бронирований и переводов было сделано с момента старта приложения, доступный по `GET /stats`.

1. Реализуй счётчики через `AtomicLong`/`AtomicInteger` вместо `synchronized`-инкремента, сравни производительность (можно просто написать бенчмарк на 1 млн инкрементов в N потоков и замерить время для synchronized vs atomic).
2. Добавь `volatile boolean maintenanceMode` — флаг, который можно включить через `POST /admin/maintenance`, и который проверяется в фоновом потоке (например, в фоновой задаче из Этапа 3) без блокировок. В README объясни, почему тут достаточно `volatile`, а не нужен `Atomic`, и в чём вообще разница между ними (atomic — для CAS-инкрементов/операций «прочитать-изменить-записать», volatile — только для видимости одиночной записи между потоками).
3. Опиши в README, что такое CAS (Compare-And-Swap) и как на нём реализован `AtomicInteger.incrementAndGet()` под капотом (не обязательно лезть в JDK, достаточно понимания идеи compareAndSet).

*Закрывает: atomic, volatile, CAS, области памяти в многопоточности (JMM, видимость между потоками).*

## Этап 6. Конкурентные коллекции

**Задание:** добавь простой in-memory кэш событий (`GET /events` должен ходить в кэш, а не всегда в БД), инвалидируемый при создании нового события.

1. Реализуй кэш на `ConcurrentHashMap` — обоснуй в README, почему не обычный `HashMap` (что именно ломается при параллельном доступе к обычной `HashMap` — вплоть до бесконечного цикла при resize в старых версиях Java).
2. Сделай второй вариант через `Collections.synchronizedMap(new HashMap<>())` и опиши разницу: `synchronizedMap` блокирует всю карту целиком на каждой операции, `ConcurrentHashMap` использует более гранулярную блокировку (сегменты/bin-ы) и не блокируется на чтение — отсюда лучшая производительность под конкурентной нагрузкой.
3. Добавь список последних 10 действий пользователей (аудит-лог) через thread-safe коллекцию — предложи и обоснуй выбор (`CopyOnWriteArrayList` подойдёт, если чтений намного больше, чем записей — самое то для аудит-лога, который читают чаще, чем пишут).

*Закрывает: synchronizedCollections, ConcurrentHashMap vs synchronizedMap, работа с коллекциями в многопоточном коде.*

## Этап 7 (бонус, если зайдёт кайф). ForkJoinPool

**Задание:** добавь эндпоинт, который считает какую-то тяжёлую агрегацию по всем событиям и бронированиям (например, суммарную выручку по категориям событий) с помощью параллельного стрима (`parallelStream()`, который под капотом использует общий `ForkJoinPool`), а также вручную через `ForkJoinPool` с `RecursiveTask` (классический пример — рекурсивная сумма по массиву).

В README сравни `ForkJoinPool` (work-stealing, для CPU-bound задач с рекурсивным разбиением) и `FixedThreadPool` (для I/O-bound задач вроде обращений к БД/сети из этапа 3) — объясни, почему для этапа 3 не стоило использовать `ForkJoinPool`.
